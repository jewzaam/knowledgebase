# Commit Type Convention Evolution

How commit type taxonomies evolved from AngularJS through Angular to Conventional Commits.

> Prescriptive rule (which types to use) lives in
> [common/commit-messages.md](https://github.com/jewzaam/standards/) in jewzaam/standards.

## The lineage

Three major sources shape today's commit type landscape:

1. **AngularJS 1.x** (defunct) — defined `chore:` and `style:` types that persisted in downstream tools but were dropped by Angular 2+
2. **Angular 2+ current** — defines 8 types (`feat`, `fix`, `build`, `ci`, `docs`, `perf`, `refactor`, `test`), no `chore` or `style`
3. **Conventional Commits 1.0.0 spec** — mandates only `feat` and `fix`, mentions "Angular convention" but doesn't specify which version

## What changed

### AngularJS → Angular 2+

Angular 2+ dropped `chore` and `style` entirely:

- **`chore`** — replaced by `build:` and `ci:` to distinguish build-system changes from CI-pipeline changes
- **`style`** — no replacement. Code formatting changes now use `refactor:` or `fix:` depending on whether they change behavior

AngularJS DEVELOPERS.md (defunct):
<https://github.com/angular/angular.js/blob/master/DEVELOPERS.md>

Angular current commit message guidelines (canonical):
<https://github.com/angular/angular/blob/main/contributing-docs/commit-message-guidelines.md>

### Why `chore` and `style` persist

`@commitlint/config-conventional` (based on Angular convention) still allows both for backwards compatibility, but neither has authoritative backing from current Angular. Persistence is inertia, not endorsement.

## Conventional Commits spec relationship

Conventional Commits 1.0.0 mandates only `feat` and `fix`. It mentions "Angular convention" but doesn't specify which version. The link effectively points at the current Angular convention, which has 8 types.

Spec: <https://www.conventionalcommits.org/en/v1.0.0/>
